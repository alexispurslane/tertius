# Code quality tooling

Epic ticket: `ter-9gj5`.

This epic adds the checks that keep the code readable: compiler checks of doc comments, reports of complex, long and duplicated code, a docs site, and a cleanup that formats and modernizes the code before every push. The user chose each tool on 2026-10-21, after a comparison of the options, and chose where each one runs on the same day.

## Where each check runs

| Stage | Check | Blocks what |
|---|---|---|
| `git commit` (`.githooks/pre-commit`) | An incremental build of the changed projects and their test projects, with every analyzer | The commit, on an error |
| `git commit` | The tests of the changed code, in Checked | The commit, on a failed test |
| `git commit` | The erosion and the verbosity of the staged tree. The post-commit hook stores them in a git note (decision 18). | Nothing. It is a record. |
| `git commit`, after the measure | The commit report, for the changed lines only: MA0051 length, and the erosion and the verbosity with the touched code that raises each (decision 20) | Nothing. It is a report. |
| `git push` (`.githooks/pre-push`) | `tools/cleanup.sh` on the C# files that the pushed commits change | The push, if the cleanup changes a file. The hook commits the cleanup, and the next push sends it. |
| `git push` | DocFX builds the docs site | The push, on a DocFX error |
| `git push` | The slop history: notes for the pushed commits, a summary against the last push, and a push of the notes (decision 18) | Nothing. It is a report. |
| Before a merge into main | `tools/test-all.sh`: every test, in Checked and Release | The merge |

The commit hook changes no file and runs only what the commit touches, so that a commit stays fast. The cleanup loads a solution, which takes 20 to 60 seconds, so it runs once per push instead.

## Decisions

1. The build writes the XML documentation file (`GenerateDocumentationFile`), so that the compiler checks every doc comment: `cref` targets, `param` and `paramref` names, and the XML itself. CS1591 (a public member without a doc comment) stays off until the doc comment rewrite, because 805 public members in `src` have none.
2. `AnalysisLevel` is `latest-recommended`, and `TreatWarningsAsErrors` is on. The root `.editorconfig` turns off each rule that flags a deliberate pattern of this codebase, with the reason in a comment above it. For example, CA1707 (the `_` character in names) stays off in test projects, because test names contain `_`. A deliberate exception in one type is a `SuppressMessage` attribute on that type, with a `Justification`. CS1573 (a `param` tag for only some parameters) is off too, because a doc comment documents only the parameters that need more than their name and type.
3. CA1502 measured the cyclomatic complexity of a method: the number of branches plus one. Its limit was 15, in `analyzers/CodeMetricsConfig.txt`. Decision 20 turned it off, and the erosion's CC took its place. Meziantou MA0051 measures the length of a method: 60 lines or 40 statements, its defaults. `MeziantouAnalysisMode=None` turns off every other Meziantou rule. Both rules are suggestions, so they never fail a build, and the existing code needs no baseline. After the first cleanup on 2026-10-21, 55 methods were over the complexity limit and 108 were over the length limit, in src, tests and benchmarks.
4. Every compile writes its diagnostics, suggestions included, to `obj/<configuration>/<framework>/analyzers.sarif` (`ErrorLog` in `Directory.Build.targets`). `tools/commit_report.py` reads MA0051 from it and prints each one whose method holds a changed line. Until decision 20, it read CA1502 too. It finds the end of a method by matching its braces. An up-to-date project does not compile again, so the file always describes the last compile, whoever ran it.
5. jscpd 5 is a Rust crate. `native/jscpd.nix` builds it from crates.io with a pinned hash, and the dev shell has it. `tools/duplicates.sh` writes an HTML and a console report of the whole code. The commit report prints only the clones in `src/` with a copy that holds a changed line. Since decision 20, it takes them from the measure of `tools/Tertius.Slop`, not from a jscpd run of its own.
6. DocFX reads the compiled assemblies and their XML files, not the source. Thus its own C# parser never meets C# 15 syntax. The site also holds ARCHITECTURE.md, GUIDE.md, tools/README.md, the design docs and the source files. DocFX is a .NET local tool, pinned in `.config/dotnet-tools.json`, because the nixpkgs build cannot start on macOS. `docfx.json` sits at the repository root, because DocFX refuses content outside the folder of its configuration. `tools/docs.sh` builds the site, and it can serve it.
7. The commit hook tests the changed code: a change in `src/Tertius.X` runs every test of `tests/Tertius.X.Tests`, and a change in a test file runs only the test classes in that file. `src/Tertius.Demo` maps to `tests/Tertius.Host.Tests`. A change in `tests/Tertius.Testing` or in the benchmarks only builds. The hook builds only those projects and the projects that they reference, so a change that breaks a project downstream shows in the full run before the merge, not in the commit.
8. The cleanup has two steps, in `tools/cleanup.sh`. First, Roslyn makes every fix that changes the code but not its meaning. `dotnet format style` applies the IDE rules: redundancies (`using` directives, `this.`, long names, parentheses, `!`), auto properties, `readonly` fields, explicit access modifiers, modifier order, `int` for `Int32`, `var` only where the type is evident, expression bodies, collection expressions, primary constructors, pattern matching, switch expressions, `using` declarations, static lambdas and local functions, readonly structs and more. `dotnet format analyzers` applies the Roslynator rules (decision 19). `.editorconfig` sets each rule to suggestion, or to warning where STYLE.md says "always" or "never", with its reason in a comment, and the script reads the list from there. One fix can make room for another, so the Roslyn step repeats until it changes nothing, at most 3 times. Then CSharpier formats the code, so its formatting wins. Roslyn's formatting rules (`IDE0055`, `IDE2000` to `IDE2006`) are off, so that nothing fights CSharpier. Some IDE rules with a fix stay off, each with its reason in `.editorconfig`. `IDE0045` and `IDE0046` turned one more `if` guard into a nested conditional expression on every run, so the cleanup never settled, and a list of guards became a chain of ternaries ten levels deep. Claude turned them off on 2026-10-24, because a list of guards reads better, and told the user. `IDE0004` (redundant casts) is off, because Roslyn 5.11 takes a cast to a C# 15 union for redundant: of the five casts that it removed, two broke the build and three made tests fail. `IDE0048` (parentheses for clarity) would put parentheses into every `a + b * c` of the math code. No rule orders members, so the order stays as the author wrote it (STYLE.md, "Member order").
9. CSharpier 1.3.0 formats the code. The dev shell takes it from nixpkgs, which has the newest release, so it needs no local dotnet tool. `.csharpierrc.yaml` sets lines of at most 120 characters, as before, and every other option keeps CSharpier's default. CSharpier also sorts the `using` directives. It cannot parse the C# 15 `union` declaration and the `closed` modifier: it reports a syntax error and leaves the file as it was. `.csharpierignore` lists the four files that hold them, so the cleanup runs, and Roslyn still fixes those files. A new file that CSharpier cannot parse stops the cleanup with an error.
10. The pre-push hook cleans the C# files that the pushed commits change, builds the solution, and commits the result as one commit. Git chose the commits to push before the hook ran, so the hook then stops the push, and the next push sends the cleanup commit too. A file with uncommitted changes stops the hook before the cleanup, so that the cleanup commit holds only the cleanup. The first cleanup of the whole codebase is one commit, and `.git-blame-ignore-revs` names it.
11. The dev shell sets `core.hooksPath` to `.githooks`. Outside the dev shell, a hook runs itself again inside it.
12. The cleanup leaves a `var` local as it is. A collection expression needs a target type, so `var x = new List<int> { 1, 2 }` keeps its initializer, and only a local with an explicit type gets the expression. The user chose this on 2026-10-22.
13. The tests run in the Checked configuration, which has Debug's contracts and Release's optimized code (`Directory.Build.targets`). The commit hook builds and tests Checked, and `tools/test-all.sh` runs Checked and Release. Debug stays unoptimized for the debugger. The user chose a third configuration over an optimized Debug on 2026-10-22. Ticket `ter-a4s2` has the measurements.
14. Every switch over a closed set (an enum, a custom `[Union]` struct or a `closed` record) fails the build when it misses a member (ticket `ter-glx8`, ARCHITECTURE.md "Switches over closed sets"). `CS8524` is off, so an enum switch expression needs no discard arm. `EnforceCodeStyleInBuild` is on with `AnalysisModeStyle` set to `None`, so the build runs only the IDE rules that `.editorconfig` raises: `IDE0010` at error, and the warnings of decision 19. Every other IDE rule stays a suggestion or off, which the build does not report. The user chose IDE0010 on 2026-10-11.
15. The commit report leaves test code out of the duplicates and the complexity, and keeps the length limit for it. A test repeats its setup on purpose, so that it reads on its own, and its branches are its checks. When the report names anything, it ends with a prompt to refactor that code in the same commit, as far as the task allows. So the code improves a little at each change that passes through it, not all at once and not never. The prompt sits in the report and not in CLAUDE.md, so that it appears only at the moment that it applies. The report names every touched method that is over a limit, not only one that the commit made worse. When most of the code is within the limits, the report can name only what gets worse. The user chose this on 2026-10-24.
16. `tools/Tertius.Slop` measures the erosion of `src` (ticket `ter-4jhz`), as the post [Measuring code sloppiness](https://earendil.com/posts/measuring-code-sloppiness/) and SlopCodeBench define it. The mass of a function is its cyclomatic complexity (CC) times the square root of its lines of code (SLOC). The erosion is the mass of the functions with CC strictly above 10, divided by the mass of all functions. A codebase with no functions has erosion 0. The program reads syntax only, with Microsoft.CodeAnalysis.CSharp 5.9.0, so it needs no build and reads all of `src` in about half a second. It prints JSON, because the commit hook will read it (ticket `ter-rnzy`). Its command line is `Tertius.Slop <metric> [root] [--text]`, so that verbosity (ticket `ter-2x99`) becomes a second subcommand beside `erosion`. The rules:
    - The CC is syntactic: 1, plus 1 for each `if`, `while`, `do`, `for`, `foreach`, `catch`, `?:`, `??`, `??=`, `&&` and `||`. A switch statement or a switch expression adds 1 as a whole, whatever its sections, arms, `when` guards and patterns. The code that a section or an arm runs, and the expression that the switch reads, still count. The user chose this on 2026-10-24, because the switch rule (decision 14) asks for one arm per case of a closed set. A metric that counted each arm would punish the code for following that rule.
    - Outside a switch, a pattern `and` or `or` adds 1, like `&&` and `||`. The pattern `x is 1 or 2` makes the same decision as `x == 1 || x == 2`, so a metric that counted only one of them would reward a rewrite that changes nothing. `not` adds nothing, like `!`. Claude chose this on 2026-10-24.
    - A function is a method, a constructor, a destructor, an operator, a conversion operator, an accessor with a body, an expression-bodied property or indexer, or a local function. A declaration without a body, such as an auto-property, holds no code, so it is no function. Code outside any function, such as a field initializer, counts in the SLOC of `src` but in no function.
    - A lambda or an anonymous method counts toward the function that holds it, because it is an expression inside that function's flow.
    - A local function is its own function, and its branches and lines are not in the function that holds it. It has a name and a signature, and a reader reads it as a unit, as a private method. If it folded into its parent, a move of code into a local function would never lower the erosion, while the same move into a private method would. The metric should not prefer one of two forms that read the same. Claude chose this on 2026-10-24.
    - The SLOC of a function counts the lines of its span that hold part of a token: not blank lines and not lines with only comments. Its attributes count, and its doc comment does not. A brace on its own line counts. Each line of a string over several lines counts.
    - The program reads every `.cs` file under `src`, but not the `obj` and `bin` folders, a file whose name ends in `.g.cs`, or a file whose comments before its first code hold `<auto-generated`. It parses with no preprocessor symbols, so the one `#if SYNC_PROFILE` block in `src` is not code.

    On 2026-10-24, the erosion of `src` was 0.364: 89 of 2,772 functions have CC above 10, and they hold 11,945 of the 32,779 mass, in 268 files with 33,633 lines of code. The post measured 0.31 ± 0.17 for established repositories and 0.68 ± 0.20 for code that agents wrote. The heaviest functions are the `AssertInvariants` methods of `EntityTable`, `FrameTree` and `World`, `JoltPhysicsBackend.UpdateGhosts`, `World.PrepareSpawn` and `PhysicsOutputCheck.Run`.
17. `tools/Tertius.Slop` also measures the verbosity of `src` (ticket `ter-2x99`), as the post defines it. The verbosity is the number of lines that a rule flags or that jscpd finds in a clone, divided by the SLOC of `src`. The SLOC is the same as the erosion's. A line counts once, however many findings and clones cover it. The rules:
    - The clone lines come from jscpd, which the tool runs on `src` with the settings `--format csharp --min-tokens 70 --mode mild` and the JSON reporter. Since decision 20, these clones are the ones that the commit report names. A clone line is a line of either copy of a clone. Without jscpd on the search path, the tool prints a message that names the dev shell and exits with code 2.
    - The flagged lines come from 48 rules that read the syntax with Roslyn, like the erosion. Each rule has an id, a one-line message that says what to write instead, and its source: STYLE.md, the user, or a rule of scb-check (github.com/gabeorlanski/scb-check).
    - Five rules also ask where a name is used: low-use-short-function, constant-argument, unused-optional-parameter, single-implementation-interface and unused-code. They read the uses in the syntax of `src`. They also read the `.cs` and `.json` files under `tests`, `benchmarks` and `scripts` as plain text, for their names. A test calls the code, and a script names events and steps that the code finds by name through reflection. A script writes a property in camel case, so a name outside `src` matches without case. A name in a string of `src` counts as a use too, because a blueprint names a field in a string. The tool builds no semantic model: a name matches by its text, so two members with one name share their uses, and such a rule flags less, never more. `measure` copies the tree's `tests`, `benchmarks` and `scripts` beside its `src` for this reason. Claude chose this on 2026-10-24 (ticket `ter-a3ya`).
    - A finding covers every line of its span, not only its first line. The span is the code that the rewrite removes or replaces, so a try statement of 30 lines is 30 verbose lines and not 1. A rule about a whole function, such as defensive-try-soup-function, flags the statements that it counts and not the whole function. The rest of the function is not what the rule calls verbose.
    - A blank line never counts, inside a finding or a clone. Five rules flag lines that hold only a comment or a directive: comment-repeats-code, doc-comment-repeats-name, commented-out-code, todo-without-ticket and region. Those lines count. So the verbosity counts such a comment, although the SLOC leaves comments out.
    - The subcommand `all` prints both reports in one JSON, from one parse of `src`. The commit hooks of ticket `ter-rnzy` run it on every commit. It takes 1.2 s, and two separate runs take 1.4 s. Claude added it on 2026-10-24, because the hook needs both numbers for one state of the tree.

    The user's first four rules:
    - pass-through-method flags a method whose whole body calls another method with its own parameters, in order. The arguments can have names, as TS0002 asks for a target with more than 3 parameters. The syntax does not show the target's parameters, so the names do not count. It also ports scb-check's trivial_wrapper.py and identity-wrapper-function. An override, an explicit interface member and a method with an attribute exist for their contract, so the rule skips them.
    - single-use-local flags a local whose name adds nothing and whose value only the next statement reads, once. Its name adds nothing when it is generic (result, res, ret, temp, tmp, value, val, data, output, obj or item), or when the next statement only returns it or passes it to a parameter of the same name. A parameter shows its name only in a named argument. The user narrowed the rule to this on 2026-10-24, because a named intermediate value makes an expression clearer (ticket `ter-a3ya`). Before, it flagged every such local: 233 findings on 382 lines, most of them names that said what the value held. The rule also skips the locals that STYLE.md asks for ("Name the parts of a complex condition"): a `bool` local, or a value that is a comparison, a pattern test or a logical operator. It also skips a value that takes its type from the declaration, such as `new()` or `[]`. A local before a loop keeps its place, because the loop runs the value again. A use in a lambda or a local function keeps it, because the value runs later. A use as a `ref` or `out` argument or as an assigned variable keeps it too.
    - comment-repeats-code flags the line comments right above a statement, with no blank line between. The comment must say what the statement says. Its words are the words of three letters or more, without common words such as "the" or "with", and without a plural s. The statement's words come from its names and keywords. A camel-case name splits into its words, and the code in its blocks does not count. The comment repeats the statement for two or more words, of which at least four fifths are words of the statement. A share of two thirds flagged six comments in `src`. Each of them gave a reason or a fact that the statement does not hold, so Claude raised the share on 2026-10-24.
    - guard-repeats-caller-check flags a null guard on a parameter whose type is not nullable, in a function outside the public API. A null guard is `ArgumentNullException.ThrowIfNull`, `?? throw`, or an `if` that tests the parameter for null and returns or throws. Nullable is on and its warnings are errors, so the compiler already made every caller in the codebase pass a value. A public or protected member and an interface member keep their guards for callers outside (STYLE.md, "Errors and contracts"). A parameter of a type parameter can hold null, so its guard stays. The coordinator suggested a check of the call sites in the same file. That check needs flow analysis of each caller. The compiler's nullable check already covers every call site in every file, so the rule reads the parameter type instead. Claude chose this on 2026-10-24.

    These rules decide their edge cases this way:
    - constant-argument and unused-optional-parameter see every call site only when every caller is in `src`: a local function, a private method, or a method outside the public API whose name no file outside `src` holds. Each use of the name must be a call, so a method group keeps its parameters. A call with one constant may vary at the next call, so constant-argument waits for two calls.
    - unused-code leaves out a private member, a parameter and a local, which the style analyzer and the compiler find (IDE0051, IDE0052, IDE0060, CS0168, CS0219). It also leaves out an override, an explicit interface member, an extern member, a class of extension members, and a member that the runtime or the compiler calls by its name, such as `Main`, `Dispose` or `GetEnumerator`. An attribute class counts as used by its name without the suffix. A member that only a test, a benchmark or a script uses counts as used. On 2026-10-24, 60 members of `src` had only such uses. The notes of ticket `ter-a3ya` list them.
    - except-pass-silence calls a report a call whose name holds Log, Write, Print, Trace, Report or Warn. Its catch clauses in a Try method stay, because a Try method reports an expected failure by its result (STYLE.md, "Expected failures"). The one new finding in `src` is `WindowPlayback.Capture`, which turns a cancellation into false: a Try method in all but its name.
    - The first form of contract-and-guard compared the names at the root of a value, so the guard on `world.Limits.MaxBodies` and the contract on `world.System` in `JoltPhysicsBackend.Grow` were one value. That was its one finding in `src`, and a false one, so Claude made a value the whole chain of names on 2026-10-24.
    - About 16 of the 35 findings of statement-wall are lists of one kind of statement, such as the assignments of a constructor, the `Array.Resize` calls for each column of `FrameTree`, or the ordered calls of a physics step, each with its comment. Such a list is one group already. The other findings are computations and setup code that blank lines would group. Fewer than half are false, so the rule stays.
    - Of the 10 findings of vague-type-name, `BodyUserData` is the one false finding: it names Jolt's "user data" of a body.
    - One of the two findings of single-implementation-interface is false: `IPhysicsOutputFacts` lets the check in Core read the entity table of Simulation, which Core cannot reference. The other, `IRangeDrawer`, has one implementation in the same module.

    The ports follow STYLE.md where it differs from scb-check:
    - defensive-function-nullable-heavy and guard-repeats-caller-check skip the public API, because a public API keeps guards that are always on.
    - boolean-return-if-else skips the last `if` of a list of guards, because STYLE.md prefers a list of early returns ("Guards").

18. The git hooks keep the erosion and the verbosity of each commit in git notes under `refs/notes/slop` (ticket `ter-rnzy`). The user chose git notes as the store. A note is one line of JSON with the erosion, the verbosity, the SLOC, the branch, the source and the time of the measurement. Decision 21 added three absolute counts to the same note. The source is `pre-commit`, `pre-push` or `seed`. Claude made the decisions below on 2026-10-24.
    - A note holds no ticket ids, although the ticket asked for them. The commit message is their one store, and git keeps it with the commit. The commands of the tool read the ids from the message with one pattern. After an amend, a copy in the note can disagree with the message.
    - The pre-commit hook measures the staged tree, not the working tree, because the commit holds the staged tree. It runs `git write-tree`, then `Tertius.Slop measure <tree>`, which measures a copy of the tree's `src` from `git archive`. The measurement runs in the background, in parallel with the tests. After the tests pass, the hook writes the tree id and the note to `slop-pending` in the git folder of the worktree. That folder belongs to one worktree, so two worktrees that commit at once never share the file.
    - The post-commit hook compares the tree of HEAD with the measured tree. If the two trees are the same, it attaches the pending note to HEAD. The hook is plain bash and never enters the dev shell. On a busy machine, the start of the dev shell took up to two minutes. Worktrees share the notes ref, so the hook tries the write five times. A failure prints a warning, and the commit stays.
    - Without a pending note, the post-commit hook attaches no note. It does not measure, because that needs the dev shell. Three kinds of commit get no note at commit time: a commit with `--no-verify`, a commit without C# changes, and a merge. Git runs no post-commit hook for a merge. If such a commit changes C# code under `src`, the pre-push hook notes it later.
    - Before the summary, the pre-push hook runs `Tertius.Slop note <last push> <tip>`. It always notes the tip. On the first-parent line after the last push, it also notes each commit that has no note and changes C# code under `src`. So the cleanup commit of decision 10 and every merge into main get a note. A commit that changes no C# code has the metrics of its parent, so it needs no note.
    - If the local clone has the commit that the remote branch names, that commit is the last push of the branch. For a new branch, the last push is the merge base with main. The summary compares the nearest noted commit on the first-parent line of the last push with that of the tip, at most 500 commits back. A commit raises a metric by the change from the nearest note before it. Decision 21 made the two ranked lists use absolute counts.
    - The pre-push hook pushes the notes with a second `git push`, after the push of the branch is chosen. Git chose the pushed refs before the hook ran, so the hook cannot add a refspec to that push. A refspec in the configuration changes every push of the clone. Before the second push, the hook fetches the remote's notes into `refs/notes/slop-remote` and merges them with the strategy `cat_sort_uniq`. That strategy keeps the lines of both notes of one commit, so notes from several worktrees and clones never conflict. A reader takes the first filled line, or the first readable line if none is filled (decision 21). Every failure in this part prints a warning and never stops the push.
    - The CSV of the history is the subcommand `history` of the tool, not a script. Thus the format of a note lives in one place. Its arguments go to `git log`, so `history --first-parent main` gives the trend line of main.

22. Type coherence and depth (ter-dyss, accepted user scope, 2026-10-30). This supersedes the earlier four-score proposal. Dependency scoring, interface burden thresholds, standalone exposure scores, method-group analysis and their calibration/defaults are removed. Class means any measured nominal source type, not only a C# class.

    TCC is the single cohesion metric: pooled direct shared instance-field pairs divided by possible visible ordinary instance-method pairs within types with instance state. Constructors are excluded. Depth is pooled WMC divided by pooled API entries over the same measured types, including types with zero API entries. WMC sums the existing `Function.Complexity` over all owned handwritten functions, of every visibility; nested types own their functions separately. Surface counts declared public/internal/protected variants of methods, constructors, operators, properties, indexers, events and fields once each, with properties counted once rather than per accessor. Inherited and synthesized members are excluded. Empty denominators are not applicable, with raw counts retained. No weighted composite is used.

    Depth and erosion remain separate. Depth is behavior weight per API entry; more branching raises WMC and therefore can raise depth without improving design. Erosion independently checks excessive function complexity. Neither metric produces an automatic quality verdict. Named types, members, functions, locations and direct shared-field pairs support later refactoring lists. `tools/README.md`, "Type coherence and source evidence", defines eligibility, counting, source-analysis limitations and unavailable-data behavior.

    Aggregate reports and named details share one counter. Historical source binds against explicit metadata without building old engine projects or reading current engine outputs. Notes retain counting/reference provenance; incompatible inputs suppress deltas. Backfill preserves existing data and unknown metadata, enriches all readable merged lines, and is idempotent. No production backfill or merge occurs in the implementation task.

    Qualitative review of 22 selected types found no validated API/dependency/parameter cutoff: EventList and DPose, SmaaPass and ToneMapPass, GeometryStore and KeplerOrbit, and ScriptCommand and DescriptorLayouts supply counterexamples. That review prompted the accepted TCC/depth direction; no reviewed cutoff becomes a quality gate.

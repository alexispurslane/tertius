# Design X adds 0.50 ms to the deck's GPU frame span, 0.20 ms above its limit

Take T17 of docs/plans/bounce-light-confidence.md, 2026-11-14, Apple M1 Max, Release, scripts/temporal-upscale-timing.json at 1920x1080 with two frames in flight, each run alone under the GPU lock. Median GPU frame span of 120 frames, main ab54c785e and the branch eccad009a in turn: main 19.007, 19.074, 18.990 ms; branch 19.536, 19.482, 19.549 ms. Difference +0.50 ms, run-to-run spread 0.08 ms. Acceptance 13 allows +0.3 ms. The gpu-clock tool was not built, so the GPU clock of the runs is not recorded.

The cost is fixed and does not come from the evidence's action: the probe build with TERTIUS_X_EVIDENCE_ACTION=0 took 19.67 and 19.52 ms against 19.65 and 19.64 ms with the action, and main's probe 19.03 and 19.09 ms.

One Metal System Trace per build (tools/gpu-trace.sh --no-counters, median busy time per pass, main then branch): filter indirect diffuse 2.011 -> 2.246 ms (+0.235); ray plan 1.335 -> 1.501 (+0.166); reflection rays 1.428 -> 1.498 (+0.070); screen trace resolve 0.293 -> 0.331 (+0.038); accumulate indirect diffuse 0.536 -> 0.568 (+0.032); accumulate indirect specular 1.401 -> 1.405; diffuse rays 1.279 -> 1.271. Every other pass is equal within 0.01 ms. The sum is +0.54 ms. One trace per build gives no spread per pass.

Open: which change of the filter and of the ray plan costs the time, and whether it can go below +0.3 ms. The files of the take are in /private/tmp/t7-3e22/x2/timing (they do not survive a restart).

## Design (line orchestrator, 2026-11-14)

### The model

The cost is fixed work that every draw does, with or without evidence. So the remedy removes work and changes no value that the renderer stores or shows. The ticket adds no feature and changes no rule of Design X.

The trace of 2026-11-14 gives the budget (median busy time per pass, main then branch, one trace per build):

| Pass | Main (ms) | Branch (ms) | Rise (ms) | What Design X added there |
|---|---:|---:|---:|---|
| filter indirect diffuse | 2.011 | 2.246 | +0.235 | Every wavelet dispatch adds two sums per tap and binds both histories. Only the feedback dispatch uses them. |
| ray plan | 1.335 | 1.501 | +0.166 | `movedSurfaceAt` at every hittable pixel: a view ray, a normalize, two projections and two image reads. |
| reflection rays | 1.428 | 1.498 | +0.070 | No reason in the code: a hit reads the same texel as before. Possibly the spread of one trace. |
| screen trace resolve | 0.293 | 0.331 | +0.038 | `movesOnScreen` reads the motion target again, and one more image store (`diffuseSampleAge`). |
| accumulate indirect diffuse | 0.536 | 0.568 | +0.032 | The block's evidence: one read, two barriers. |

The target is a rise of at most 0.30 ms against main. The run-to-run spread is 0.08 ms, so aim for 0.25 ms or less.

### Cut A, the filter: the feedback dispatch is a pipeline, not a branch

Who owns what stays: `DiffuseFilter` owns the dispatches, and `DiffuseFilter.FeedbackDispatch` names the one dispatch that writes the slow history's light and the fast history's retained deviation. Today that choice travels to the shader as the push constant `feedback`, so all six dispatches of the thin kernel compile the feedback's sums and bind both histories. After the cut the choice is the pipeline: the plain dispatches run a shader without the sums and without any history, and the feedback dispatch runs the shader with them. The push constant goes, so the choice has one store.

```csharp
internal sealed class DiffuseFilterKernel
{
    public static readonly DiffuseFilterKernel Thin;   // six dispatches, 3 x 3
    public static readonly DiffuseFilterKernel Wide;   // five dispatches, 5 x 5

    /// <summary>The shader of the plain wavelet dispatches: it moves the light and its variance between the filter's
    /// own images, and reads and writes no history.</summary>
    public string WaveletShader { get; }

    /// <summary>The shader of dispatch <see cref="DiffuseFilter.FeedbackDispatch"/>: the same step, which also writes
    /// the light into the slow history and the retained deviation into the fast history.</summary>
    public string FeedbackShader { get; }
}

/// <summary>The push constants of a wavelet dispatch.</summary>
internal struct DiffuseFilterPushConstants
{
    /// <summary>The distance between the kernel's taps, in pixels: 2^i in dispatch i.</summary>
    public int Step;
}
```

- `diffuse_filter_wavelet.glsl` keeps one `main`. The symbol `TERTIUS_FILTER_FEEDBACK` selects the feedback's sums, its two history bindings and its stores at compile time. Each kernel gets one more small `.comp` file that defines the symbol.
- `DiffuseFilter` holds two wavelet pipelines and picks one per dispatch from `FeedbackDispatch`.
- A plain dispatch no longer touches a history, so its barriers on the slow and the fast history go, if the Vulkan specification allows it for a shader that does not access them. Write to the specification, not to MoltenVK (CLAUDE.md, "Design preferences"). Read the memory note `moltenvk-barrier-ends-encoder.md` first.
- The feedback dispatch still reads and writes the fast history's texel to change only its alpha. Leave that: the retained deviation has one store, the fast history's alpha.

### Cut B, the ray plan: the moved mark from values that the plan already holds

`movedSurfaceAt(pixel)` rebuilds the pixel's surface point and reads the motion target, although the plan holds both for every traced pixel (`tracingPixelAt`, `reprojectionsAt`). Give the rule the values:

```glsl
// Whether a surface point moved since the last draw (docs/plans/bounce-light-confidence.md, section 8.4): `point` is
// the point relative to this frame's eye, in m, and `target` is its pixel's motion target. The rule is movedSurfaceAt's.
bool movedSurface(vec3 point, vec4 target);
```

The rule and its thresholds (`LeastMotion`, `MotionRounding`) do not change, and every mark keeps its value. `movedSurfaceAt(pixel)` can stay as the form for a pixel that the plan does not trace (an impostor), built on `movedSurface`.

Only if cuts A and B leave the rise above 0.30 ms: move the owner of the two motion facts. The surface test pass already holds the view ray, the distance and the motion target of every pixel, and it decides how a pixel's surface relates to the last frame. It can write the moved mark and the resolve's `movesOnScreen` as two more bits of the surface test image, which every reader loads already. The image's 8 bits are all in use (`signals.glsl`, bits 0 to 3 and 4 to 7), so its format becomes R16UI, and `accumulate_temporal.comp`, which reads all bits, masks its 8.

```glsl
// signals.glsl
const uint SurfaceMoved = 0x100u;          // the pixel's surface moved since the last draw (movedSurface)
const uint SurfaceMovesOnScreen = 0x200u;  // the pixel's point moves on screen by LeastMotion pixels or more
```

I rejected two other stores. The motion target's w already holds the place choice as a float, and flags beside it need arithmetic at every reader. A per-instance flag from the CPU misses deforming meshes and needs a G-buffer bit.

### Order of the work, and what to measure

1. Measure first: one more GPU trace of the branch and of main, to see the spread of the per-pass numbers above. `tools/gpu-trace.sh` needs `TERTIUS_DIFFUSE_FILTER=on` in the environment (bug t0-8jfj).
2. Cut A, red-green where a test can tell (a test that the plain dispatches bind no history, if the validation tests can show it; the existing filter tests must stay green without a change of any expected value). Measure the frame span against the branch before the cut.
3. Cut B, the same way. The moved-mark tests of `ScreenTraceRenderTests` hold the rule.
4. If the rise is still above 0.30 ms, the surface test move, with a note of the reason in the report. If a cut gives less than the spread, drop it and say so.
5. The last measurement, as take T17 ran: `tools/demo-timing.sh <out> scripts/temporal-upscale-timing.json --size 1920x1080 --in-flight 2`, Release, each run alone under the GPU lock, main `ab54c785e` and the ticket's head in turn, three rounds (main, head, head, main, main, head). And one GPU trace per build.

### Acceptance

1. The median GPU frame span of the deck rises by at most 0.30 ms against main `ab54c785e`, as the mean of three rounds, with the six medians in the report.
2. No stored or shown value changes: every test passes in Checked and then in Release with no expected value changed and no reference image approved again. The survey still `rect-lamps` gives the same specks and blotch as the branch before the ticket, to three digits.
3. No validation message in the GPU tests, no new device feature, and every shader compiles with `-Werror`.
4. Coverage of the changed lines, and one `tools/mutate.py` list for them (tools/README.md, "Mutation testing"), with the table in the ticket note.
5. ARCHITECTURE.md and docs/plans/bounce-light-confidence.md (section 7, the filter, and acceptance 13) say what the code does.

Out of scope: any change of what evidence does, the remedy for the bay film's trail (t0-acxm), the G-buffer's formats, and the accumulation's evidence read (+0.03 ms).

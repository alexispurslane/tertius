# Tertius

Tertius is a game engine in C# for space-scale scenes and dense immersive-sim interactions at once. It runs on Jolt Physics in double precision and draws with a deferred Vulkan renderer. It is an engine, not a game. It is unfinished, and it changes fast.

The two tables below say what is different about its physics and its entity-component system. They also say which other engines do something similar.

## Physics

Other engines do some of the things that Tertius does. I found no engine that does all of them.

| Feature | In Tertius | Who else |
|---|---|---|
| 1. Large worlds | Each object keeps its position relative to a frame near it. When a group of slow objects is 8,389 km or more from its frame, the engine automatically makes a new frame at its center. So every object is correct to 2 nanometers, at every place, at the same time. That number is the limit of the number format, not a measured error. Two levels of frames are enough for the whole observable universe. One frame holds the universe. One frame holds each region up to about a million light-years across, such as a galaxy. The engine makes all other frames itself. | **Star Citizen, in part.** Objects in its ships and on its planets keep positions relative to them. I found no source that it makes new frames by itself. If it does not, a loose object far from any ship or planet, such as a drifting crate, uses one center point: the center of its star system. Then that object is correct only as much as in the engines below. Unreal Engine 5, Godot (custom build), Flax and Stormworks use one center point. They are correct to 2 nanometers only within 16,777 km of it. They are correct to 1 mm at the distance of Neptune, and to 8 m at the nearest star. Unity is correct to 1 mm only within 16 km. Kerbal Space Program moves the center point with the player, so only objects near the player are correct. |
| 2. Ships in ships | Each planet, ship, station and room can be a real object with its own frame: an area that moves with the object. A frame is not a separate level. It stays in the larger world, so you can see into it from outside. It follows its object. A frame that the engine makes for a fast ship falls freely, and the ship falls with it. You can walk in a ship that flies inside a larger ship, and a crate can float out of the door into space. | **Star Citizen does a similar thing with ship and planet frames.** I found no source that its frames touch across an edge (item 3), or that it makes frames by itself (item 4). Unity, Godot, Flax and Jolt can run separate physics worlds, but they do not move objects between them, and the worlds do not follow anything. Void Crew lets you walk in a moving ship, but not in ships in ships. |
| 3. Objects across an edge | A crate can be half in a ship and half outside. It can touch objects on both sides at the same time. | **None that I found in a game or engine.** A 2021 research paper (Kaufmann and others) copies objects across the borders of fixed areas in a large world. Its areas do not move. |
| 4. Fast objects | A ship in orbit moves 8 km each second. Most physics engines store speeds in 32-bit numbers, such as PhysX (used by Unity), Jolt (used by Godot) and Box3D. At orbit speed, those numbers cause two problems in any engine. Small pushes have no effect. A person who uses a thruster for one minute can end about 10 m from the correct place. That number is an estimate, for the harder of two directions that the measurements tried. Tertius fixes this. Objects that move fast together, such as ships in a battle or a boarding party, share one moving frame. The engine makes it automatically, at every place at the same time. So their motion relative to each other stays correct. | **Kerbal Space Program, in part.** It fixes this only in the area around the player's ship. Ships farther than about 2.5 km stop using physics and move on fixed paths. Star Citizen probably fixes it inside its ships, because objects there move relative to the ship. I found no other engine that tries. So in other engines, a space battle, a spacewalk or a boarding party at orbit speed gets these errors. |
| 5. Thrust that you feel | When a ship increases speed, the crew feels a push toward the back wall. When the engines stop in orbit, the crew floats. The tests prove this with loose crates, not yet with a person. | **None that I found.** Star Citizen and Space Engineers use areas of fake gravity. Fake gravity is a setting of the ship, not a result of its motion. |
| 6. Orbits and turns | Planets and stations move on calculated orbits and turn at constant speeds. | **Kerbal Space Program, Kitten Space Agency, Orbiter.** In Kerbal Space Program, a ship on a fixed path stops using physics, so nothing on it can move. Orbiter has no ship insides to walk in. In Tertius, a station on a fixed path still has full physics inside. |
| 7. Spin gravity (not complete) | In a turning station, you will stand on the outer wall. A ball that you drop will move in a curve. Today, a turning station carries what rests on it, but it gives no gravity yet. | **Small test projects, and an experimental Unreal tool for hair and cloth only.** Outer Wilds gets a similar result, because its planets turn in one shared world. That world uses Unity, so the limits of item 1 apply. Space Engineers uses fake gravity, so a dropped ball falls straight down. |

The sources are developer posts, patch notes and forums. I did not make sure that all of them are correct.

## Entity-component system

Each entity is a handle into tables of engine data, plus a list of component classes that hold its behavior. Entities affect each other only through messages.

| Feature | In Tertius | Who else |
|---|---|---|
| Behavior in components | Each entity has a list of component classes that share one interface, as in Caves of Qud. The components handle the entity's messages in priority order. Each one can change, remove or add a message, and only the components after it see the change. An entity with nothing to handle does not run. | **Caves of Qud is the model.** There, a part is a C# class, and a part can change an event or stop it. Unity and Unreal also put behavior on the object, in MonoBehaviour and ActorComponent. Bevy, flecs, EnTT, Unity DOTS and Unreal Mass put behavior in systems that run over packed arrays, and their components hold only data. Tertius packs only its engine tables, such as transforms. In Tertius, a new component can react to any message to its entity with no change to other code, so behavior can emerge. In engines with systems, a programmer must write each interaction between kinds of entities into a system ahead of time. |
| Entities change only themselves | A component writes only its own entity. `Self`, its view of the entity, has write members for that entity only. The write methods of `World` throw during a tick. To change another entity, a component sends it a message. | **None that I found enforces this.** In Caves of Qud, a part acts on its own object, but only by convention. Godot advises signals, but it also allows direct method calls on other nodes. Flecs advises that observers do not change components. So in Tertius, only an entity's own components decide what happens to it, and gameplay runs in parallel without locks. Where any object can write any other, game code needs locks or one thread, and the result depends on the update order. |
| Messages that allocate nothing | A message is a small struct: a target, a sender, a type id and a 48-byte inline payload. The payload holds one unmanaged struct, a struct with no references to heap objects. The target is a custom C# union of an entity, a topic or a broadcast, so C# never boxes it. A topic is a list of subscribers, and every frame has one. The router stores each message once and writes one (recipient, message) pair for each recipient. A message arrives on the next tick, or later with `SendAfter`. | **None that I found has entity, topic and broadcast targets and an inline payload.** Unreal Mass signals go to entities and can wait, but they carry only a name. Bevy messages and the EnTT dispatcher are typed queues, but they do not go to an entity. Flecs sends an event to one entity with a pointer to its payload. Caves of Qud events and Unity `SendMessage` arrive at once. So in Tertius, a dense scene can send many messages with data each tick, and they give the garbage collector no work. With a signal that has only a name, or a queue with no target, game code must move the data or find the recipient. |
| Everyone reads the last tick | The entity tables that change during a tick have two copies: transforms, render data, physics intents (the forces and velocities that a component asks physics for), component flags and collision groups. During a tick, components read the front copy, which holds the end of the last tick. Each entity writes only its own rows in the back copy. Other entities do not see those writes until the next tick. Between ticks, the engine copies forward only the rows that were written. So the order in which entities run does not change what they read. Entity queries also run on the front copy. | **None that I found.** Flecs and Unreal Mass delay the addition and removal of entities and components to a sync point. But Flecs systems can still change component values in place. Bevy keeps two copies of its message queues only. In Unity, Unreal and Godot, an update can see neighbors that already updated in this frame, so the update order matters. In Tertius, the update order does not change the result, so gameplay can run in parallel and stay deterministic. Where the order matters, gameplay usually runs on one thread, and a change to the update order can change the game. |
| Deterministic parallel gameplay | Gameplay runs on worker threads, in chunks of 64 entities by default. Each chunk keeps its own list of sent messages and its own slots for new entities. The step between two ticks joins them in chunk order. A test of 200 ticks on real Jolt gets the same world hash with one worker and with eight, on one machine. | **None that I found promises the same result on any number of threads.** Unity DOTS is the nearest. It sorts the commands that parallel jobs record by chunk index, but its docs promise that order for playback only. Bevy sets no order for parallel systems, and Unreal sets none inside a tick group. Flecs merges per-thread command queues at sync points. Caves of Qud and Dwarf Fortress run their simulation on one thread. So in Tertius, you can replay a run from the same inputs and see a bug again, on one machine, with any number of threads. In parallel engines without that promise, a bug that depends on thread timing can change or vanish on the next run. |
| Handles that catch stale references | An entity is a handle: a slot index and a generation that goes up each time the table frees the slot. The transform, render and physics data lie in arrays indexed by slot. Every call that takes a handle checks the generation, in every build. A stale handle gives an exception or false. A message to it reaches nobody, even after a new entity takes the slot. | **None that I found checks every access in every build.** Bevy, Unity Entities, flecs and EnTT also use generations. Bevy warns that a reused id can alias, and EnTT leaves most calls on a stale id unspecified. Flecs fails most operations on a dead handle. Unreal clears UPROPERTY pointers to a destroyed object, and Godot raises an error on a freed one. So in Tertius, a bug with a stale handle shows at once. Without the check, a call can act on a new entity that took the old slot, and the bug shows far from its cause. |
| Frames are entities | A frame is a coordinate system that moves with its object, such as a planet, ship, station or room. Each frame is an ordinary entity with an extra handle into the frame tree, where each frame has a pose in its parent. So a frame has components, gets messages and is destroyed like any other entity. What was in a destroyed frame moves to the nearest frame above it that survives. Every read of a position or velocity names the frame that it is relative to. The engine converts through the frame tree in doubles. | **None that I found.** The nearest is big_space for Bevy, where each grid is an entity. But I found no velocity reads, no physics for each grid and no read relative to any chosen frame. Star Citizen's physics grids follow ships, but I found nothing that says a grid is an ordinary entity. Unity DOTS, Bevy and Unreal read positions only relative to the parent or the world. In Tertius, a ship and its frame are one entity, which gets messages and has components like any other. Where a frame is a separate object, game code must keep it in step with its ship and remove it with the ship. |
| Blueprints | A blueprint is a list of component types with field values, and it can inherit from a parent. Registration uses reflection to check it and compiles one factory per component type and field set. A spawn then calls these factories, and a tick uses no reflection. | **Caves of Qud is close.** Its blueprint XML names parts, and the game loads them through reflection. Qud also compiles the C# source of mods at run time, and Tertius does not do that yet. Unreal Mass builds entities from templates with traits. I found no source on whether Qud or Mass compiles factories ahead of time. So in Tertius, content describes each kind of entity as data, and a spawn costs no reflection, even in a busy tick. |
| Hot paths allocate nothing in C# | C# has a garbage collector, and a collection can pause a frame. So after its buffers grow to their working size, a tick allocates nothing on the heap. That covers messages, event filters such as `EventList.Of<T>()`, entity queries and the physics step with contacts. Tests count the allocated bytes and expect zero. One test ticks 2,000 busy entities. Two others count the bytes of all threads during physics steps with many contacts. | **None that I found does all of it in a language with a garbage collector.** Unity DOTS systems that use Burst allocate no garbage-collected memory, but I found no built-in entity messages in its docs. Friflo ECS, a C# library, reports zero allocations after its buffers grow. Bevy, flecs and EnTT have no garbage collector. I found no other engine that checks this with allocation tests. So in Tertius, gameplay and physics give the garbage collector no work, and they cause no pauses. In a C# engine whose game code allocates each frame, the collector pauses the game from time to time. |

The sources are engine manuals, developer interviews and wikis. I did not make sure that all of them are correct.

To make sure that these claims are real, read [GUIDE.md](GUIDE.md). It names the code and the tests behind each one.

## Build and run

Every command runs in the Nix dev shell from [flake.nix](flake.nix), in the repository root. You need Nix with flakes turned on. The first run needs network access, because the dev shell builds the double-precision Jolt library. The renderer and the Rendering and Host tests need a Vulkan device. On macOS, the dev shell supplies MoltenVK.

```sh
# Build the solution.
nix develop --command bash -c 'dotnet build Tertius.slnx'

# Run the tests of one module: Core, Simulation, Physics, Rendering or Host.
nix develop --command bash -c 'dotnet test --project tests/Tertius.Core.Tests'

# Run a demo script with no window. It writes PNG images and JSON state dumps.
nix develop --command bash -c 'dotnet run --project src/Tertius.Demo -- --script scripts/drop-box.json --headless --out captures/drop-box'

# Run a scene in a window. W, A, S and D move, V changes the view, F1 starts a fly camera, and Esc quits.
nix develop --command bash -c 'dotnet run --project src/Tertius.Demo -- --scene station'
```

[tools/README.md](tools/README.md) gives the commands for coverage, mutation testing and JetBrains Rider.

## Repository layout

- [src](src) holds the modules. Tertius.Core holds the math, handles, messages and the frame tree, and it depends on nothing. Tertius.Simulation, Tertius.Physics and Tertius.Rendering each depend only on Core. Tertius.Host holds the window, the threads and the script runner, and Tertius.Demo holds the demo scenes.
- [tests](tests) holds one xUnit project per module.
- [ARCHITECTURE.md](ARCHITECTURE.md) is the binding design, and [docs/plans](docs/plans) holds the design docs.
- [scripts](scripts) holds the JSON scripts for the demo scenes.
- [tools](tools) holds the helpers for coverage and mutation testing, and [native](native) builds the Jolt library.
